What You Built 01

You built a command-line tool that copies everything you've made on Replicate onto your own disk. It asks Replicate's API for your prediction history, one page at a time, saves the whole history as a JSON file, then downloads every output file of every successful prediction into a folder per model and zips each folder. Run it with --last-run and it only fetches what's new since the last complete run.

Replicate deletes data from API-made predictions after about an hour; website predictions are kept. Your tool is the copy that stays.

The stack, in plain EnglishOne Node.js file (index.js), run with npx replicate-downloader. Three dependencies: commander reads the flags, dotenv loads your token from a .env file, archiver makes the zips. Everything else, including the HTTP calls, uses what Node 18+ already has: fetch and streams.

The metaphor: the archive run. You send an archivist into a gallery that throws work away. They copy the ledger page by page and write an index of everything in it. Four porters carry the pieces home into drawers, one per model, and box each drawer. On the way out, the archivist leaves a bookmark so next week's run knows where to start.

Where the metaphor breaks: a bookmark marks a page; yours marks a moment, the time the last complete run started. Nothing records which files you already have.

Follow One Run 03

It's Sunday. You open a terminal in your archive folder and run npx replicate-downloader --last-run. Last Sunday's run finished cleanly. Since then you made one image set on the website: two images from flux-dev, prompt “a lighthouse in fog, risograph”. Here is everything that happens.

1
index.js · main()

Read the token and the flags

Before main() runs, dotenv.config() copies .env into process.env, and commander parses your flags into options. main() checks three things: the token is set (otherwise it prints how to set it and stops), --last-run isn't combined with --since or --until, and --source is web or api. Then it builds new ReplicateDownloader(token, { lastRun: true }) and calls run().

2
getDateFilterParams() · loadState() · parseDate()

Open the bookmark, turn it into a query

Because lastRun is set, the ledger reads .replicate-downloader-state.json and finds lastSuccessfulRun: "2026-09-20T18:04:11.532Z". parseDate normalises it to ISO. Then one second is subtracted:

const sinceBuffer = new Date(new Date(parsedSince).getTime() - 1000);
params.append('created_after', sinceBuffer.toISOString());

The result is a query string: created_after=2026-09-20T18:04:10.532Z. That second of overlap means a prediction created at exactly the bookmark's instant is fetched, not lost. getDateFilterBounds() computes the same bound again, for the check in hop 4.

3
fetchAllPredictions() · makeRequest()

Copy the ledger, page by page

First it stamps this.fetchStartTime with the current time. That becomes next week's bookmark. Then it loops (simplified):

while (nextUrl) {
    const response = await this.makeRequest(nextUrl);
    this.allPredictions.push(...response.results);
    nextUrl = response.next;          // a cursor URL, or null on the last page
    await new Promise(r => setTimeout(r, CONFIG.requestDelay));  // 200 ms
}

makeRequest sends Authorization: Bearer <token> and a User-Agent with the version. A non-OK status becomes a thrown Error carrying Replicate's detail message. Three details sit around that core loop. If the next URL has lost the date filter, the filter is appended again. If every prediction on a page is older than the bound, it stops early. And if any request throws, it logs the error and breaks, leaving fetchComplete false. This week there is one page, with your one prediction.

4
fetchAllPredictions(), after the loop

Check the dates again, on your side

The server has already filtered by date, but the ledger filters once more: anything with created_at before the bound or after --until is dropped. A prediction with no created_at is kept. Dates are compared as ISO strings, which sort the same way as the times they name.

5
saveEnhancedMetadata() · buildMetadata()

Write the index

Every prediction is grouped by model name. extractModelName takes the last part of prediction.model (black-forest-labs/flux-dev → flux-dev), falling back to version.model, then the urls.get path, then unknown-model. Statuses are counted under their real API names. The file looks like this:

{ "exported_at": "2026-09-27T17:30:02.118Z", "total_predictions": 1,
  "model_stats": { "flux-dev": { "total": 1, "succeeded": 1, "failed": 0, "canceled": 0 } },
  "predictions_by_model": { "flux-dev": [ { "id": "q7x2m4ab…", "prompt_summary":
      "a-lighthouse-in-fog-risograph", "has_output": true, … } ] },
  "raw_predictions": [ …every field Replicate returned… ] }

Failed and canceled predictions are in here too, and so is the output of models that return text rather than file URLs. The index is the only place that text is saved.

6
downloadAndOrganizeOutputs() · extractOutputUrls()

Turn predictions into a job list

Only predictions with status === 'succeeded' and an output go forward. For each one, the model's folder is created, then extractOutputUrls walks the output, whatever its shape:

const collect = (value) => {
    if (typeof value === 'string') { if (value.startsWith('http')) urls.push(value); }
    else if (Array.isArray(value)) value.forEach(collect);
    else if (value && typeof value === 'object') Object.values(value).forEach(collect);
};

Your output is { images: [url1, url2] }, so you get two jobs: { url, prediction, modelName: 'flux-dev', modelDir, fileIndex: 0 } and the same with fileIndex: 1.

7
the worker pool · generateFilename() · downloadFile()

Four porters, one shared list

The pool is four async functions reading the same counter (simplified):

const worker = async () => {
    while (nextJob < jobs.length) {
        const job = jobs[nextJob++];
        try { await this.downloadFile(job.url, job.modelDir, baseName); … }
        catch (e) { totalErrors++; }        // log it, take the next job
    }
};
await Promise.all(Array.from({ length: Math.min(4, jobs.length) }, worker));

Each worker waits for its own download before taking another job, so at most four files are ever in flight. Taking a job (jobs[nextJob++]) happens with no await in the middle, and Node runs one piece of JavaScript at a time, so two workers can never take the same job. Here only two workers start, because there are only two jobs.

The name comes from generateFilename: date, model, prompt slug, the first eight characters of the ID, and _2 for the second file. 2026-09-24_flux-dev_a-lighthouse-in-fog-risograph_q7x2m4ab. The extension is added in downloadFile: from the URL if it has a sane one, else from the Content-Type header (image/jpeg → jpg), else bin. The body is streamed to disk with pipeline(), counting bytes as they pass. A bad status throws before any file is opened. A stream failure deletes the half-written file.

8
createModelZip() · run()

Box the drawers, leave the bookmark

Each model folder is zipped with archiver at level 9, as by-model/flux-dev.zip. run() prints a summary (files, errors, size per model, status counts). Last, it writes the bookmark, but only under two conditions:

if (this.fetchComplete && successful > 0) {
    this.saveState({ lastSuccessfulRun: this.fetchStartTime, … });
}

The new bookmark is the moment hop 3 started. Anything you create while the run is going is newer than that, so next Sunday picks it up. And if the ledger broke off halfway, the old bookmark stays, so next Sunday re-covers the gap.

Loose Ends 06

What the code does today that you'll probably want to change. None of it loses data.

  • confirmed A date-only --until leaves out that day. "2024-01-31" parses to midnight at the start of the 31st (UTC), so the README's January example stops at the 30th. Fix: when --until has no time, add a day.
  • confirmed Text outputs get an empty drawer. A language model's output is a list of strings, not URLs, so no files are downloaded. The model's folder is still created, and zipped empty. The text is safe in the index.
  • confirmed Settings the code never reads. .env.example lists five options (REQUEST_DELAY and others), and CONFIG.enhancedMetadata exists, but only the token is read from the environment. The README also draws the zips one level higher than where they land.
  • confirmed Exit code 0 on a missing token or a crash. Scripts running it on a schedule can't tell those apart from success. A run whose fetch fails outright does exit 1.

Where you'd go next

  • Save text outputs as .txt → a branch in downloadAndOrganizeOutputs for predictions whose extractOutputUrls list is empty.
  • Skip files already on disk → a check before downloadFile in the worker.
  • Retries → around await this.downloadFile(…) in the worker. From here, explain-diff covers each change.

Answer Key 08

Stamp rule. Explain-how answers: Draft 2 hits every must-hit point (your wording, any order) and none of the traps. The first four: the “stamp if” line.
01 · Find itThe Drawers
Answer
downloadFile() picks the extension: first extensionFromUrl() (the URL's last path segment), then extensionFromContentType() (the response header), and bin only if both give nothing (e.g. application/octet-stream). The base name comes from generateFilename().
Stamp if
Both fallbacks, in order, and generateFilename.
02 · Predict itThe Ledger
Answer
created_after=2026-03-08T11:59:59.000Z (two days back, minus the one-second overlap; the exact milliseconds depend on the clock). If a whole page is older than the bound, pagination stops early and the client-side filter drops those predictions.
Stamp if
The parameter name, the minus-one-second, and the early stop.
03 · Predict itThe Bookmark
Answer
The loop logs the error and breaks; fetchComplete stays false. Predictions from pages 1–2 are still indexed and downloaded. The bookmark is not written, so next week starts from the old bookmark and fetches the gap again (re-downloading pages 1–2 is harmless).
Stamp if
Partial download, bookmark untouched, next run starts from the old mark.
04 · Trace itThe Porters
Answer
The worker's downloadFile sees !response.ok and throws before opening any file. The worker's catch logs it and adds to totalErrors, then its while loop takes the next job. The other workers never notice. Promise.all resolves when all four run out of jobs; the summary shows 9 downloaded, 1 error.
Stamp if
No file written, error counted, the same worker keeps going.
05 · Explain howThe Drawers
Must hit
  • A folder named with today's date, with a subfolder (and a zip) for each model.
  • Every file from every successful prediction, named date_model_prompt_id.
  • One JSON file listing every prediction, including failed ones and text answers.
  • It lands in whatever folder you ran it from.
Traps
“It backs up your account” (it's predictions only). Leaving out the JSON, which is where text outputs live.
Altitude
No API words. One example filename beats a description of the pattern.
06 · Explain howThe Bookmark
Must hit
  • --last-run reads a small file holding one timestamp.
  • It asks Replicate only for predictions created after that time (minus a second).
  • The timestamp saved is when the run started, so things you make mid-run are caught next time.
  • It's only saved if the whole list came through, so a dropped connection means next time starts from the old mark.
Proper names
High-water mark · incremental sync.
Traps
“It remembers which files it downloaded” (it stores a time, not a list). “It saves when it finishes” (it saves the start time).
Altitude
Say “a timestamp in a file,” not .replicate-downloader-state.json.
07 · Explain howThe Ledger
Must hit
  • GET /v1/predictions with a Bearer token; dates go in as created_after / created_before, plus source.
  • Follow the next cursor until it's null, re-adding the filters if the cursor dropped them, with a 200 ms pause.
  • Stop early if a whole page is older than the bound, then re-filter locally.
  • Any error stops paging and marks the fetch incomplete.
Proper names
Cursor pagination · defense in depth.
Traps
“Page numbers” (it's a cursor URL). Skipping what happens on an error.
Altitude
They'll want parameter names. Say them.
08 · Explain howThe Porters
Must hit
  • Build a flat list of jobs, one per output URL.
  • Start four async workers; each takes the next job from a shared index and awaits it before taking another, so at most four are in flight.
  • Taking a job has no await in it, so on Node's single thread two workers can't take the same one.
  • Each file streams to disk; a failure is counted and the worker moves on. Promise.all waits for all four.
Proper names
Worker pool · bounded concurrency · streaming.
Traps
“Promise.all on every download” (that's unbounded). “Threads.”
Altitude
Mention the test that proves the limit if they ask how you know.

Talking Points 09

For when you're stuck, not for reciting. Where your Draft 2 says it better, cross mine out.

One sentence

I wrote a command-line tool that copies your whole Replicate history, every image, clip and prompt, onto your own disk, and on later runs only fetches what's new.

Thirty seconds · non-technical

Replicate is where a lot of people run AI image and audio models, and it doesn't keep everything forever. My tool asks it for your whole history, saves a list of everything you've made, then downloads every file into a folder per model with names built from the date and the prompt. Run it again next week and it picks up where it left off.

Two minutes · technical listener

It's a single Node file with three dependencies. It pages through Replicate's predictions endpoint by following the next cursor, with date filters sent as created_after and created_before and re-checked locally. It writes the history to a JSON index, then flattens every successful output into a list of download jobs. Four async workers pull from that list and stream each file to disk, taking the extension from the URL or the content type. For incremental runs it saves a high-water mark: the time the last complete fetch started. If a fetch breaks off, the mark isn't moved, so nothing is skipped.

Questions you'll get asked

“Does it need my password?”

No. It uses an API token you create on Replicate, read from an environment variable or a .env file, and never written anywhere.

“Will it download the same thing twice?”

With --last-run, only across an interrupted run, on purpose. Without it, it fetches everything each time.

“What doesn't it do yet?”

Text outputs live only in the JSON index, and there's no retry for a failed download. Both are small changes in one function.
